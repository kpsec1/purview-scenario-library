## Recommended sequence

This scenario adds exactly **one rule** to a policy owned by
`scenarios/dspm-for-ai/copilot-sensitive-data-exposure/`. Every rollback stage below is scoped to
that one rule only, the parent policy and its Rule 0 (label exclusion) / Rule 1 (web-grounding
restriction) are never modified by this scenario's scripts, in either direction.

### Stage 1, Disable (reversible, seconds)

```powershell
Connect-IPPSSession -AppId $AppId -Certificate $Cert -Organization $TenantDomain
./deploy/Remove-CopilotPromptFullBlockRule.ps1
```

This runs `Set-DlpComplianceRule -Identity "Copilot-Block-SensitivePrompts-FullResponse" -Disabled $true`.
The rule remains defined (visible in the Purview portal, on the parent policy's rule list) but stops
evaluating Copilot traffic. Re-enable instantly:

```powershell
Set-DlpComplianceRule -Identity "Copilot-Block-SensitivePrompts-FullResponse" -Disabled $false
```

Use this stage for: a false-positive spike needing immediate relief, a change freeze, or while
comparing this script's `RestrictAccess` output against a portal-created rule per `README.md` §5's
VERIFY guidance.

### Stage 2, Permanent removal (not reversible)

```powershell
./deploy/Remove-CopilotPromptFullBlockRule.ps1 -Purge
```

This runs `Remove-DlpComplianceRule -Identity "Copilot-Block-SensitivePrompts-FullResponse"`, which
deletes **only this rule**. The parent policy and its other two rules are unaffected and continue
enforcing exactly as they did before this scenario was deployed. There is no undo, re-establishing
this control means re-running `deploy/Add-CopilotPromptFullBlockRule.ps1` from scratch.

## What rollback does **not** undo

- **Audit log / alert history.** Alerts already generated by this rule are retained per their own
  retention windows regardless of the rule's state.
- **Responses already blocked.** A Copilot prompt that was already refused while this rule was
  enforcing is not retroactively re-processed; disabling or removing the rule afterward only affects
  future prompts.
- **The parent policy and its Rule 0/Rule 1.** Neither rollback stage touches
  `Copilot DLP - Sensitive Data Exposure Protection`'s existence, `Mode`, or its label-exclusion /
  web-grounding-restriction rules, those are owned and rolled back independently by
  `scenarios/dspm-for-ai/copilot-sensitive-data-exposure/rollback.md`.

## Verification after rollback

```powershell
Get-DlpComplianceRule -Identity "Copilot-Block-SensitivePrompts-FullResponse" |
    Select-Object Name, Disabled, Priority
```

Confirm `Disabled` reports `True` (Stage 1) or that the command returns nothing (Stage 2). Then
confirm the parent policy is untouched:

```powershell
Get-DlpCompliancePolicy -Identity "Copilot DLP - Sensitive Data Exposure Protection" | Select-Object Name, Mode
Get-DlpComplianceRule -Policy "Copilot DLP - Sensitive Data Exposure Protection" | Select-Object Name, Priority, Disabled
```

The two parent-scenario rules (`Copilot-Exclude-Labeled-Content`,
`Copilot-Restrict-WebGrounding-SensitivePrompts`) should still be present and in the same state they
were in before this scenario was deployed.
